# Metrics are queued raw and collapsed to delta data points per batch

Metrics reuse the log pipeline: every instrument call is one queued measurement, batched by the same `batch` thresholds, sent to its own derived `/metrics` endpoint (a trailing `/logs` becomes `/metrics`, or `metricsEndpoint`; extends ADR 0001). When a batch is sent, the encoder collapses it into delta data points, one per metric and attribute set. Each measurement remembers where the previous measurement of its series ended, so a data point covers that gap up to the last measurement in the batch: consecutive batches of a series meet without gaps or overlap, and the state lives in the meter, so retries and the page-unload split cannot advance it twice. Instruments of one kind, name and unit are one metric, and the first one defines its description and histogram boundaries. Som sends delta only, so cumulative backends need the collector's `deltatocumulative` processor.

We rejected the OTel SDK model (an in-memory aggregator exported on an interval) because it needs a second timer and lifecycle beside the batcher. We rejected one data point per call because delta points with equal timestamps and attributes are duplicates in the OTLP data model. The cost is that the aggregation window is the batch window, not a fixed interval, that a measurement dropped from a full queue leaves a gap in its series, and that the meter keeps one timestamp per series. Instrument calls never throw, like `span.end()`.
